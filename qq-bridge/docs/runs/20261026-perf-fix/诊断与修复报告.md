## 一、结论先说

| # | 症状 | 真正根因 | 处理 |
|---|---|---|---|
| 1 | 回复慢（12–13 秒/条） | 桥接的 `qq_wait_for_messages` 在**新消息到达之后**还会强制等一个「静默窗口」才把消息交给模型；`config.json` 里 `socialV2.wait.minQuietAfterNewMs = 10000` 是**硬下限**，即使模型传 `quietMs=0` 也会被抬到 10 秒 | 已修：`minQuietAfterNewMs`→2500、`defaultQuietMs`→2500 → 实测 **4–5 秒/条** |
| 2 | DSH 报错 | 桥接配置的 provider 是 `deepseek-account`，但**本机 DSH 的模型目录里没有这个 provider**（目录只有 `deepseek-official` / `deepseek-modlens`）→ 每轮 `session.selectModel` 必然失败两次（`session/model-unavailable`） | 已修：`dsh.provider`→`deepseek-official` → 报错归零 |
| 3 | DSH 刷屏上万条 | DSH 0.2.1 的 skill-filesystem provider 列举 **app.asar 里的自带 skills 目录**时抛 BigInt 错误（`Cannot mix BigInt and other types`）→ 整个 provider 被跳过 → 用户自己的 skills（`~/.dsh/skills`、`~/.agents/skills`，各 8+ 个）加载不了 | 已修：patch 里把 `bundledSkillDir` 指到 asar 之外；`restart-dsh.ps1` 补 `DSH_BUNDLED_SKILL_DIR` 环境变量（宿主组合实例用） |
| 4 | 越聊越慢 | QQ 会话上下文已涨到 **59,904 token 缓存命中**（turn 5 / step 37 / seq 486），会话一直没被压缩重建 | 已处理：重启 DSH 使旧会话作废，下一条消息开干净会话 |
| 5 | 会话繁忙时迟迟不回 | `socialV2.autoReplyCheckMs = 30000`（busy 队列的回复检查间隔 30 秒）+ 日志里的「30s/45s 后检查」 | 已修：→10000 |

## 二、延迟是怎么来的（逐步拆解）

链路：QQ → NapCat(OneBot11) → bridge.js → MCP `qq_wait_for_messages` → DSH 模型 → `qq_send_message` → QQ

修复前（10 次采样一致）：
- QQ 端可见延迟 **12–13 秒**
- `qq_send_message` 本身只花 **0.17–0.21 秒**（不是 QQ 发送慢）
- `qq_wait_for_messages(timeoutMs=300000)` 调用→返回 **71 秒**，而消息在返回前 **10 秒**就到�� → 慢在 wait 工具内部

代码定位（`qq-bridge/src/bridge.js`）：
- L7433-7440：`minQuietAfterNewMs` 是静默窗**下限**；`quietMs = max(minQuietAfterNewMs, 模型传入值)` → 模型传 0 也没用
- L10445-10456 `suggestQuietMsV2()`：默认 8000；「句子没说完」或「15 秒内连发 ≥3 条」→ 12000
- L7484-7490：新消息到达后 `while (Date.now() - lastNewAt < quietMs)` 继续等 → **这 10 秒是硬等**

修复后实测（`qq-activity.log`）：
| 收到消息 | 发出回复 | 耗时 |
|---|---|---|
| 16:52:26 | 16:52:30 | 4 s |
| 16:53:33 | 16:53:37 | 4 s |
| 16:53:59 | 16:54:04 | 5 s |

（修复前同一时段为 12–13 s）
防抢话保护保留：连发 3 条 / 句子未完 → 仍走 12 秒窗口；群聊语境下行为不变差。

## 三、DSH 侧的真实问题（用 DSH 自己的模型目录取证）

直接调 DSH 的 `session.modelCatalog` RPC 拿到权威目录：

```
default:  provider=deepseek-official  model=deepseek-flash  reasoningEffort=off
routableProviders: ["deepseek-official", "deepseek-modlens"]
  deepseek-official: deepseek-flash (DeepSeek-V4.1-Flash), deepseek-v4-pro (DeepSeek-V4-Pro)
  deepseek-modlens : deepseek-v4-pro (vision)
failures: []
```

→ **`deepseek-account` 根本不存在**，所以 bridge 每轮 selectModel 必失败两次（16:12 / 16:18 / 16:25 / 16:42 各两条日志），修复后 bridge.log 中该错误计数为 **0**。

DSH 日志（`%APPDATA%\dsh-desktop\logs\harness.log`）其它发现：
- `skill-registry ... cannot list "...app.asar\...\dsh-agent-preset\skills": Cannot mix BigInt and other types` —— 累计 **10991 条**（10-17 至 10-26），属 DSH 自身在 asar 内列举目录的 bug；本机打补丁只能绕开宿主实例，env var 才是根治
- `dsh-switchman: /ctx-handover: this session's preset exposes no /compact command` —— 用户自己那个 DSH 会话的 preset 没暴露 /compact（**QQ 那个 preset 是有的**，L413-424 挂了 compaction-basic + command-compact）
- `dsh-desktop-workbenches: Workbench catalog fetch failed` —— 联网抓不到 workbench 目录（无害）
- `patch: entry "open-sea-skin" not found` —— DSH 升级后的残留条目（无害）

## 六、遗留问题与建议（本轮未动）

1. **开机不会自启**：注册表 Run 只有 `QQNT`（主号）；bot 小号的 NapCat、qq-bridge、DSH Desktop 都没有自启项 → 机器重启后机器人不会自己起来。**建议加一个开机脚本**（顺序：DSH → NapCat → bridge）。
2. **QQ 掉线无人看守**：桥接看门狗只能自愈 token/配置，救不了 QQ 进程 → 建议加一个检查 `3001` 端口并拉起 `launcher-user.bat` 的计划任务（每 2 分钟）。
3. **DSH 端口不固定**：DSH 桌面版每次启动可能换端口（本次恰好仍是 43129），而 `config.dsh.baseUrl` 是写死的 → 端口一变机器人就哑。需做动态发现（`discoverDshLaunchToken` 同一套逻辑已在 dsh-client.js 里）。
4. **用户自己的 DSH 会话没有 /compact** → 上下文只增不减，越聊越慢。QQ preset 已有 compaction ✓。
5. **`restart.bat` 有坑**：它只杀 `Name='node.exe'`，而现在桥接是以 `DSH Desktop.exe`（ELECTRON_RUN_AS_NODE）跑的 → 直接用会起**双实例**互相抢消息。本轮改用「按 PID + 按命令行匹配」的方式重启。
